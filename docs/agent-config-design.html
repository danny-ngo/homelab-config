Technical design · 2 October 2026 · Proposed implementation

Agent configuration across machines and harnesses

Build a dedicated, versioned collection of personal instructions and skills, apply explicit machine profiles, and review upstream changes without losing local adaptations.

This document specifies the proposed system. The discussion produced a handoff document; it did not implement the new repository, installer, or upstream updater.

1. Ownership and boundaries

Agent-config

Own canonical skills, reusable prompts, instruction fragments, profiles, adapters, upstream snapshots, and provenance.

Provide a standalone apply command and upstream review tooling.

Ansible / homelab-config

Install prerequisites, obtain a pinned checkout, choose a profile, and run apply as the target user.

Record the deployed revision. Keep machine access and provisioning here.

Dotfiles and project repositories

Dotfiles remain configuration-only. Project repositories own their project-specific instructions and skills.

Credentials, sessions, and caches stay outside the agent-config repository.

The initial suggestion to bootstrap through dotfiles is superseded by the existing configuration-only dotfiles boundary. External provisioning is the integration point.

3. Profiles and installation

Profiles explicitly select harnesses, skills, and instruction fragments. Compose a base profile with additions and exclusions; define deterministic inheritance and reject cycles or destination collisions. Provisioning chooses the profile rather than inferring it from a hostname.

Workstation

Direct directory symlinks

Link selected curated skill directories into each verified harness location. Editing a linked checkout becomes visible immediately.

Useful while authoring skills. A Git checkout update can also change linked content before another apply.

Managed node

Revision-specific installation

Copy selected content into an immutable release directory, validate it, then switch managed links to that release.

Updates become active at explicit apply. Keep a prior release for rollback and validate the entire selection before switching.

  1. Resolve profile and construct the complete installation plan.
  2. Validate selected content, destination paths, prerequisites, and ownership conflicts.
  3. Dry-run reports additions, changes, removals, and conflicts without writing state.
  4. Apply links/copies and rendered instructions; record profile, revision, destinations, and fingerprints.
  5. Reapply makes no changes. Profile switching removes only unchanged outputs owned by this tool.

Refuse to overwrite unmanaged files or manually changed managed outputs. Test against temporary homes. Importing or reviewing upstream changes never changes the installed setup.

4. Record ancestry per influence

Each influence connects an exact upstream file and section to the local material it informed. Use heading paths to distinguish repeated headings; extraction must specify whether child subsections are included. Missing or ambiguous sections become review tasks.

Generate exact adaptation diffs from source snapshots and local content. Keep rationale in provenance rather than manually duplicating a patch that can drift.

5. Upstream review and merge

Prepare an isolated branch or worktree with a review packet. Fetch candidate commits, inspect licenses and supporting resources, and preserve all unresolved evidence. Never execute imported scripts merely to import a skill.

View A · Your adaptation

Baseline upstream → current local section

Shows what you deleted, changed, and added. Offer line and word views; textual modifications appear as removed and added text.

View B · Upstream evolution

Last reviewed upstream → candidate upstream

Shows new changes requiring assessment. Also retain baseline → candidate when preparing a merge.

View C · Proposed adoption

Current local skill → proposed local skill

Shows the exact downstream change to approve, alongside source attribution and adopted/omitted rationale.

Adapted content: three-way merge

Use baseline upstream as base, current local content as ours, and candidate upstream as theirs. Only use this when a meaningful textual ancestry exists. Merge extracted sections in staging, then replace the local section after resolution.

If reviewed_revision is ahead of baseline_revision, the merge can propose previously omitted changes again. Carry those decisions into the review packet. After a completed rebase onto the candidate, advance the baseline and record retained omissions as local adaptations.

A clean textual merge still needs workflow review. Overlapping edits, renamed headings, binary resources, and removed dependencies need explicit handling.

Inspired or blended content: reviewed synthesis

Show each source’s changes and the mapped local sections. Ask an agent or reviewer to propose a minimal coherent patch, identify conflicts, and explain omissions. Do not merge an entire synthesized skill against an arbitrary upstream file.

Own the orchestration instructions. Keep separable upstream-derived checklists in attributed references so those blocks can have clearer merge ancestry.

  1. Fetch and pin candidates; validate source paths, references, and notices.
  2. Generate the three views and affected-section report.
  3. Prepare automatic textual merges where justified; otherwise propose synthesis.
  4. Resolve conflicts and review adopted, adapted, and omitted changes.
  5. Validate the final skill and commit snapshots, provenance, lock updates, and curated content together.

The first implementation should use Git diffs and a Markdown review packet. A dedicated HTML diff interface can follow once the data model and update behavior are proven.

Choices still needed

  • Repository destination: local path, hosting, and visibility.
  • Initial adapters: Codex is a reasonable first candidate; confirm the actual harness set.
  • First sources: real repositories, selected skill directories, and verified redistribution permissions.
  • Implementation runtime: choose a small CLI stack compatible with the intended machines.
  • Deployment defaults: direct links for authoring machines and revision-specific releases for managed nodes are the proposed defaults.

Material failure modes

  • Upstream heading changes make mappings ambiguous: stop extraction and request remapping.
  • Large rewrites make patches noisy: use reviewed synthesis and preserve rationale.
  • Tool or permission assumptions conflict across sources: reconcile the complete workflow before applying.
  • Existing harness content collides: fail safely and report it rather than adopting it.
  • One shared source has multiple dependent skills: track review status per influence; do not globally mark every dependent as reviewed.
