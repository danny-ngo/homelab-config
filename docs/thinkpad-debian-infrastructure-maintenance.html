01 · Posture

Protect state, then restore service

The ThinkPad is the production convergence point for K3s server state and Docker service data. A fast but destructive repair is a failure if the backup is stale, the datastore token is lost, or the only service data is overwritten.

Always true

  • The MacBook remains the Ansible controller.
  • Backups are checked before mutation.
  • APT transactions are complete and attended.
  • K3s server changes precede worker changes.
  • Tailscale is a private management path; Tailscale SSH remains disabled.
  • State paths and secrets never appear in public logs.
  • Reboots happen with console recovery practical.

Never normal

  • Running upgrades immediately before travel.
  • Pruning Docker volumes to recover routine space.
  • Editing rendered K3s config as the lasting fix.
  • Upgrading every cluster node in one blind step.
  • Copying a live database without its consistency method.
  • Regenerating K3s state before preserving failed data.
Recovery order. Stabilize storage and power, preserve evidence, restore the ThinkPad OS, restore the K3s server and token, validate the API, rejoin workers, restore Docker service state, then reconcile applications.

Backup and change gate

  • The latest off-host backup completed and its destination is reachable.
  • The backup covers the K3s SQLite database, matching /var/lib/rancher/k3s/server/token, config, and each Docker state path.
  • Important services have current application-level dumps or snapshots.
  • The rollback artifact or previous Git revision is known.
  • Physical console and recovery media are available for boot-chain changes.
  • The maintenance window includes validation and rollback time.

04 · Routine procedure

Perform a controlled Debian update

1

Preview and review

Read Debian security advisories and stable release notes relevant to installed packages. Refresh metadata, inspect origins, simulate the transaction, and stop if removals are surprising.

sudo apt update
apt list --upgradable
apt-cache policy
sudo apt-get --simulate full-upgrade

Review Tailscale separately because the role configures its official third-party APT source. Debian-native Docker remains on Debian’s repositories.

2

Upgrade and read the result

sudo apt full-upgrade
sudo dpkg --audit
systemctl --failed
sudo journalctl -p err --since '1 hour ago' --no-pager
find /etc -xdev -type f \( -name '*.dpkg-dist' -o -name '*.dpkg-old' -o -name '*.ucf-dist' \) -print

Resolve package configuration files deliberately. Preserve the Ansible-managed version unless a reviewed repository change adopts the new default. Do not restart services repeatedly without understanding which stateful operations are active.

3

Reconcile desired state

From the MacBook, validate and reapply the profile so a package change cannot leave silent drift. These commands assume the configured become method works non-interactively; otherwise use the setup guide’s --ask-become-pass variants.

make ci
./bootstrap.sh --profile infra --check
./bootstrap.sh --profile infra
make validate LIMIT=thinkpad
4

Reboot under observation

Reboot when the kernel, systemd, firmware-facing libraries, container runtime, or maintenance plan requires it. Drain or pause sensitive application work first.

sudo systemctl reboot

Watch LAN reachability from another device. If the host misses its normal return time plus two minutes, switch to the physical console; do not keep issuing remote reboot commands.

5

Smoke-test production

uptime
uname -a
systemctl --failed
systemctl is-active ssh tailscaled docker k3s
sudo docker ps
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A
sudo k3s kubectl get --raw=/readyz
journalctl -b -p err --no-pager

Finish with service-specific health checks and one real read-only application query. Process state alone does not prove data-path health.

05 · Hardware lifecycle

Treat firmware as a boot-chain change

Firmware tooling is not currently owned by the repository. If fwupd and smartmontools are adopted, add them to reviewed automation before relying on these procedures.

Firmware review

fwupdmgr get-devices
fwupdmgr refresh
fwupdmgr get-updates
Read the vendor release notes. Apply updates only on AC power with a healthy battery, current backup, local console, and recovery media. Do not interrupt a capsule update.

Storage and thermals

sudo smartctl --scan
sudo smartctl -x DEVICE
cat /sys/class/thermal/thermal_zone*/temp
cat /sys/class/power_supply/BAT*/capacity
cat /sys/class/power_supply/BAT*/status
Replace DEVICE with the explicit scanned device. Escalate increasing media errors, critical warnings, unsafe temperature, swelling, or rapidly degrading battery capacity.
After firmware. Re-enter firmware settings, confirm UEFI/Secure Boot, virtualization, Wake-on-LAN, boot order, and AC-loss behavior, then repeat the complete reboot smoke test.

07 · Cluster lifecycle

Upgrade the server before workers

The repository installs a checksum-pinned K3s binary. Do not bypass that contract with the upstream convenience installer. Change the pinned version, architecture checksums, and relevant documentation in a reviewed commit.

1

Prepare the cluster

sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A
sudo k3s kubectl get --raw=/readyz
/usr/local/bin/k3s --version

Read K3s release notes and Kubernetes version-skew policy. Do not skip unsupported minor versions. Verify the current datastore-plus-token backup and record the old binary checksum.

2

Review the repository change

Update both server and agent checksum maps for every supported architecture. Run make ci, review check mode, then apply only to the ThinkPad first.

make ci
make check PLAYBOOK=ansible/playbooks/k3s.yml LIMIT=thinkpad
make k3s LIMIT=thinkpad
make validate LIMIT=thinkpad
3

Prove the server, then roll workers

Require API readiness and normal workloads before changing any agent. Upgrade one Pi 3 worker at a time; wait for Ready and application recovery before the next.

ssh thinkpad 'sudo k3s kubectl get --raw=/readyz'
ssh thinkpad 'sudo k3s kubectl get nodes -o wide'
ssh thinkpad 'sudo k3s kubectl get pods -A'
make k3s LIMIT=pi3a
ssh thinkpad 'sudo k3s kubectl wait node/pi3a --for=condition=Ready --timeout=5m'
Rollback is a state operation. If the new version changed the datastore incompatibly, restoring only the old binary is insufficient. Stop K3s, preserve the failed state, restore the matching pre-upgrade datastore and token, restore the previous verified binary/config, then start and validate. Follow the K3s recovery runbook.

08 · Durability

Verify backups by restoring them

A green backup job proves that bytes were copied. The quarterly drill proves that the bytes are sufficient, decryptable, internally consistent, and usable by the expected software.

K3s

  • SQLite database directory.
  • Matching server token.
  • Server config and pinned version.
  • Restore to isolated storage.
  • API and object validation.

Docker services

  • Product-aware dump or snapshot.
  • Persistent path inventory.
  • Runtime secret recovery.
  • Clean service instance.
  • Application-level query.

Host recovery

  • Inventory and encrypted Vault.
  • Disk and mount declarations.
  • SSH trust records.
  • Debian and firmware versions.
  • Recovery guide offline.

Quarterly restore acceptance

  • Select a recent backup without using files from the live ThinkPad.
  • Restore into a clean, isolated location with documented credentials.
  • Verify ownership, permissions, versions, and checksums where applicable.
  • Start only the isolated recovery target; prevent it from impersonating production.
  • Run K3s API/object checks and a service-specific data query.
  • Record backup ID, restore duration, result, missing steps, and corrective owner.
  • Securely dispose of temporary restored secrets and data after acceptance.

10 · Laptop power

Use the battery as a signal, not a strategy

The initial Debian preparation installs the lid-close policy and reloads systemd-logind without ending active sessions. The infrastructure profile continues to own /etc/systemd/logind.conf.d/60-homelab-lid.conf. After manually changing the file, reload systemd-logind before testing the effective behavior.

cat /sys/class/power_supply/AC*/online 2>/dev/null || true
cat /sys/class/power_supply/BAT*/status 2>/dev/null || true
cat /sys/class/power_supply/BAT*/capacity 2>/dev/null || true
sudo systemctl reload systemd-logind.service
systemd-analyze cat-config systemd/logind.conf
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitch
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitchExternalPower
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitchDocked
  • Investigate unexpected battery discharge while AC is reported online.
  • Keep the lid policy explicit and retest after systemd or firmware changes.
  • Keep air paths clear and do not operate a swollen or physically damaged battery.
  • Define a measured low-battery shutdown threshold and alert path before automating it.
  • After a real outage, inspect the previous boot with journalctl -b -1, filesystems, Docker, K3s, and backup freshness.

11 · Incident entry

Preserve evidence before changing state

  1. Confirm blast radius from an independent machine: host, LAN, Tailscale, Docker service, K3s API, worker, or application.
  2. Record the time, last known good state, recent OS/config/deployment changes, power event, and backup ID.
  3. Use the least invasive access path: existing SSH session, new LAN SSH, Tailscale, physical console, then recovery USB.
  4. Capture systemctl --failed, relevant journal, mounts, space, sockets, Docker state, and K3s state without exposing secrets.
  5. Stop retry loops that create more writes. Preserve failed disks, databases, K3s data, and container logs before replacement.
  6. Choose repair, rollback, or restore based on state safety—not on which command is fastest.
Do not improvise destructive cleanup. Never remove K3s data, Docker volumes, filesystem metadata, package databases, or failed-state directories until an exact backup exists and the recovery owner approves the target.

12 · Incident procedure

Host does not return after reboot

  1. Check power and firmware state

    Verify AC, battery, Ethernet link, display output, boot order, storage detection, Secure Boot state, and any pending firmware capsule screen. Do not power-cycle during an active firmware update.

  2. Use the Debian boot menu

    Try the previous installed kernel from advanced options. If it boots, preserve the failing boot journal and package logs before making changes.

    journalctl -b -1 -p err --no-pager
grep -E ' install | upgrade | remove ' /var/log/dpkg.log | tail -n 100
ls -l /boot

  3. Use recovery media

    Boot the verified Debian USB, identify filesystems by UUID and label, unlock encryption if used, and mount read-only first. Copy logs and critical state before repair. Never format or initialize a disk because it is not immediately mountable.

  4. Repair only the confirmed layer

    Bootloader, initramfs, filesystem, and disk failures have different remedies. If hardware health is suspect, clone or replace the device before write-heavy filesystem repair.

  5. Validate the full platform

    After boot, run the OS smoke test, Ansible validation, K3s API checks, Docker service checks, and a new backup. A successful login alone does not close the incident.

13 · Incident procedure

LAN, Tailscale, or SSH is unavailable

Physical and LAN

ip -brief link
ip -brief address
ip route
cat /etc/resolv.conf
systemctl --type=service --state=running | grep -E 'NetworkManager|networking|systemd-networkd'
Check cable, link LEDs, switch/router lease, reservation, address conflict, gateway, and DNS separately. Inspect only the network manager actually active on this installation.

SSH and firewall

systemctl status ssh
ss -lntp
sudo sshd -t
sudo ufw status verbose
journalctl -u ssh -b
Keep the console session while correcting policy. Do not disable the firewall merely to see whether access returns.

Tailscale

systemctl status tailscaled
tailscale status
tailscale netcheck
journalctl -u tailscaled -b
Tailscale is a management path, not the K3s worker endpoint. Restore LAN identity before cluster traffic.

If the SSH host key changed unexpectedly, stop. Verify whether the OS was rebuilt or keys were deliberately rotated through a trusted console before updating known_hosts.

14 · Incident procedure

Docker or a stateful stack is unhealthy

  1. Separate daemon failure from one Compose project: inspect systemctl status docker, docker info, and docker ps --all.
  2. Inspect the relevant unit and container logs with a bounded time range; confirm filesystem space, inodes, mounts, and permissions.
  3. Identify the exact deployed image digest, Compose definition revision, environment/secret source, and last successful backup.
  4. Do not recreate or remove volumes. If a migration failed, stop writers and follow the product’s restore/rollback procedure.
  5. Restart only the failing layer after its dependency and data state are understood. Repeated restarts can amplify corruption or lockout.
  6. Close with container health, application-level read/write behavior as appropriate, dependency checks, and a post-incident backup.
systemctl status docker
journalctl -u docker --since '1 hour ago' --no-pager
sudo docker ps --all --no-trunc
sudo docker inspect CONTAINER
sudo docker logs --since 1h CONTAINER
findmnt /srv
df -h /srv
df -ih /srv

15 · Incident procedure

K3s API or cluster is unhealthy

  1. Confirm host prerequisites

    systemctl status k3s
journalctl -u k3s --since '1 hour ago' --no-pager
findmnt -T /var/lib/rancher/k3s
df -h /var/lib/rancher/k3s
df -ih /var/lib/rancher/k3s

  2. Test local API and nodes

    sudo k3s kubectl get --raw=/readyz
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A
sudo k3s kubectl get events -A --sort-by=.lastTimestamp

  3. Protect datastore evidence

    Before reinstalling, removing, or generating a fresh server, stop write-heavy recovery attempts and preserve /var/lib/rancher/k3s, the matching token, config, binary checksum, and journal through the protected incident path.

  4. Restore the server first

    Use the documented K3s server recovery. Require local API readiness before rejoining or changing a worker. A fresh server without the old datastore is a new cluster.

  5. Reconcile workloads last

    After control-plane recovery, verify node architecture/Ready state, system pods, persistent volumes, secrets, services, ingress, and an application-level transaction.

16 · Incident procedure

Root or data storage is full

  1. Stop the noisiest non-critical writer if it is actively consuming the final space. Preserve logs and identify its owner first.
  2. Check blocks and inodes, then inspect only the affected filesystem with du -x. Include deleted-open files with lsof +L1.
  3. Use the owner-specific actions in the capacity table. Free a small, known-safe amount, then stabilize the service before deeper cleanup.
  4. Do not delete unknown data under K3s, Docker, /srv, /var/lib, or /boot. Do not prune volumes.
  5. After recovery, fix retention or capacity, run data-integrity checks, restart deliberately, validate applications, and confirm backups resume.
Full disk can be a data incident. SQLite databases, container logs, image extraction, and package operations may be left incomplete. Inspect their integrity and logs instead of assuming that freeing space repaired them.

17 · Lifecycle

Rebuild or retire without losing identity

Rebuild sequence

  1. Preserve failed hardware and state where practical. Record the last backup, Git revision, package versions, K3s pin, disk layout, firmware, and host-key status.
  2. Restore Debian with the same hostname, architecture, intended LAN address, and storage paths by following the setup guide.
  3. Verify the new SSH host key at the console; replace the MacBook trust entry only after the rebuild is confirmed.
  4. Apply baseline and infrastructure automation. Stop empty K3s and Docker services before restoring protected production state.
  5. Restore the K3s datastore and matching token, validate the API, then reconnect workers.
  6. Restore Docker services in dependency order and pass application-level tests before reopening deployments.

Retirement sequence

  1. Migrate and restore-test every service; confirm no backup or deployment job still targets the host.
  2. Drain/delete the K3s node as appropriate, revoke Tailscale identity and restricted SSH identities, remove router reservation and Wake-on-LAN target, and update inventory.
  3. Archive the final configuration and restore evidence according to retention policy.
  4. Erase internal storage with a method appropriate to the device and data classification; record completion before reuse or disposal.
