01 · Target design

Know what this machine owns

The ThinkPad is a managed production target, not an Ansible controller or a general-purpose workstation. The MacBook owns provisioning. The ThinkCentre owns disposable development. This host owns durable runtime state.

Hardware
ThinkPad with an Intel Core i5-8250U-class x86_64 CPU, SSD storage, working battery, and wired Ethernet for steady-state service.
Operating system
Debian 13 “trixie” amd64, minimal server installation, systemd, distribution kernel, no graphical desktop.
Network
Stable router reservation for the wired interface. K3s server and worker traffic use the LAN address. Tailscale provides private remote management and does not replace the LAN cluster endpoint.
Docker
Debian’s docker.io, docker-cli, and docker-compose packages. Definitions live beneath /opt/infra/containers; persistent application data lives beneath /srv/infra/data.
K3s
One checksum-pinned server binary, default single-server SQLite datastore, and configuration managed by this repository. Pi 3 workers join later over the LAN.
Administration
Normal access is SSH from the MacBook with strict host-key checking. Tailscale SSH is disabled. Helm administration normally runs from the MacBook with protected, purpose-scoped credentials.
This is a destructive installation. The Debian installer may erase the selected disk. Verify the disk model, serial, capacity, and backup before changing a partition table.

02 · Before mutation

Resolve decisions automation cannot make safely

The repository intentionally leaves production storage and backup targets site-specific. Record these choices outside the machine before installing any stateful service.

DecisionRecommended setup postureGate
Disk encryptionUse guided encrypted LVM if physical theft is in scope and someone can unlock the machine after an unattended reboot. Otherwise document why an always-on server uses unencrypted root and protect secrets at rest separately.Recovery and reboot behavior are understood and tested.
Filesystem layoutKeep the initial layout simple. Root needs headroom for images, K3s, APT, and logs. Add a separate data device only through storage_mounts.Every device uses a stable UUID or mapper path, never an assumed device name.
Backup destinationChoose encrypted off-host storage, retention, notification, and restore ownership. The laptop’s battery is not a backup.A clean-location restore succeeds before production data is admitted.
Recovery accessKeep local console and SSH key access. Disable SSH passwords only after both are proved.ssh_recovery_access_confirmed remains false until the second path works.
Secure BootEither keep the Debian-supported boot path enabled or document a deliberate exception. Do not copy the ThinkCentre’s firmware choice automatically.The installed kernel boots after firmware and package updates.
No production-state shortcut. Until the backup architecture in open decisions is closed and tested, install the platform but do not place irreplaceable databases, automation metadata, or sole-copy credentials beneath /srv.

03 · Hardware and media

Prepare a recoverable installation

  1. Record the hardware identity

    Capture the exact ThinkPad model, serial, firmware revision, CPU, RAM, storage model and health, battery health, wired NIC and MAC address. Keep the record with recovery notes, not only on the laptop.

  2. Update and configure firmware

    • Use UEFI boot; disable legacy/CSM mode.
    • Enable CPU virtualization and IOMMU features.
    • Enable Wake-on-LAN and wired link in the intended sleep/off state.
    • Set power-on-after-AC-loss behavior for an infrastructure host.
    • Keep USB boot available and record any Secure Boot change.

  3. Create trusted Debian media

    Download the current Debian 13 amd64 netinst image and matching checksum/signature from Debian. Verify it before writing the USB. Keep the installer and a known-good Ethernet adapter as recovery media.

  4. Reserve the network identity

    Plan hostname thinkpad. Create a router reservation for the wired MAC and record its address as THINKPAD_LAN_IP. Confirm the LAN, K3s pod, and K3s service CIDRs do not overlap.

At the machine

Debian USB, Ethernet, AC power, local display/keyboard access, firmware password if configured, and the verified administrator SSH public key.

On the MacBook

Current repository checkout, encrypted production inventory, Vault password source, verified backup destination, and router and Tailscale administration.

04 · Debian installer

Install a minimal Debian 13 server

  1. Boot the installer in UEFI mode

    Select the UEFI entry for the USB. Confirm wired networking and the SSD are detected; stop if the target disk is ambiguous.

  2. Set identity and locale

    Use hostname thinkpad, leave the DNS domain blank unless the production local domain already operates, and select America/Toronto. Leave the root password blank so Debian disables direct root login and grants the first account sudo access, then create administrator account homelab.

  3. Partition deliberately

    Choose the recorded storage design. Guided partitioning with one root filesystem is the simplest recovery path; guided encrypted LVM is appropriate only with an accepted console-unlock plan. Review the final table before approving writes.

  4. Select only server tasks

    Install SSH server and standard system utilities. Deselect every desktop environment and web server. Use Debian’s default bootloader path on the selected internal disk.

  5. Capture the first boot

    Remove the USB, boot from disk, unlock encryption if selected, and log in locally. Confirm identity, storage, time, network, and UEFI mode.

    hostnamectl
cat /etc/os-release
uname -m
findmnt /
timedatectl
ip -brief address
[ -d /sys/firmware/efi ] && echo UEFI

05 · First boot

Patch, identify, and prove remote access

sudo apt update
sudo apt full-upgrade
sudo systemctl reboot

After reboot, install the small diagnostic set needed before automation and inspect the host:

sudo apt install --yes ca-certificates curl git openssh-server pciutils usbutils
systemctl --failed
systemctl is-enabled ssh
systemctl is-active ssh
lsblk -o NAME,MODEL,SERIAL,SIZE,FSTYPE,FSVER,MOUNTPOINTS
findmnt --verify
journalctl -b -p err --no-pager

Trust the host key through the console

Display the ED25519 host-key fingerprint at the ThinkPad console, compare it when connecting from the MacBook, and add the verified key. Do not learn a persistent infrastructure host key with blind accept-new.

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

From the MacBook, prove key authentication in a second session, then validate sudo interactively. Debian’s normal sudo policy asks for the homelab password.

ssh homelab@THINKPAD_LAN_IP
ssh homelab@THINKPAD_LAN_IP 'hostname; id'
ssh -t homelab@THINKPAD_LAN_IP 'sudo -v && sudo id'
Keep the console session available. Do not close the only working path until a fresh SSH connection succeeds and production inventory points at the reserved address.

06 · Laptop-specific behavior

Make the lid and battery boring

A closed lid must not suspend an infrastructure server. The battery provides short ride-through, but it also needs monitoring and is not an indefinite UPS.

  1. Activate it during one-line preparation

    The Linux preparation one-liner detects the ThinkPad lid switch, installs /etc/systemd/logind.conf.d/60-homelab-lid.conf with HandleLidSwitch=ignore, HandleLidSwitchExternalPower=ignore, and HandleLidSwitchDocked=ignore, then safely reloads systemd-logind. Wait for the message Lid-close ignore policy is active; the lid can now be closed. before putting the ThinkPad away. The infrastructure role owns the same file afterward and keeps the policy persistent.

  2. Inspect the effective policy

    systemd-analyze cat-config systemd/logind.conf
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitch
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitchExternalPower
busctl get-property org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager HandleLidSwitchDocked

    All three properties must report ignore. A desktop or power daemon can hold a lid inhibitor lock, but the minimal server installation deliberately has no desktop power manager.

  3. Validate real behavior

    Start a continuous ping from another LAN machine, close the lid on AC power for several minutes, and confirm SSH, Docker, and K3s stay reachable. Repeat after any systemd or firmware change. Keep vents unobstructed.

  4. Record power signals

    upower -e 2>/dev/null || true
cat /sys/class/power_supply/BAT*/capacity 2>/dev/null || true
cat /sys/class/power_supply/BAT*/status 2>/dev/null || true

    Choose and test the sustained-outage shutdown policy before an outage occurs.

Remaining power gaps. Firmware tooling, SMART tooling, battery alerting, and low-battery shutdown are not currently managed by a role. Record any manual change as drift and promote it into automation before calling the setup fully reproducible.

07 · Managed-node preparation

Prepare Linux, then return control to the MacBook

Run the standalone installer as homelab on the ThinkPad. It uses a temporary source archive, installs managed-node prerequisites, global uv, the user’s pinned Python, and the detected-laptop lid safety policy. It does not retain a checkout or install Ansible.

curl -fsSL https://raw.githubusercontent.com/danny-ngo/homelab-config/main/install.sh | bash

command -v uv
uv --version
uv python find 3.14
python3 --version

On this ThinkPad, preparation detects the physical lid switch and activates the persistent lid-close ignore policy before it exits. Once the success message says the lid can be closed, no controller-side Ansible run or reboot is required before closing it.

Ownership boundary. Debian’s /usr/bin/python3 runs Ansible modules. uv-managed Python is for user workloads. Do not install Debian’s Ansible package or make the ThinkPad a second controller.

08 · Controller preparation

Describe the real host without publishing it

Perform these steps in the persistent MacBook checkout. Production addresses, enrollment credentials, hashes, backup endpoints, and real keys stay out of public documentation and example inventory.

  1. Initialize and review inventory

    make init-inventory
$EDITOR ansible/inventories/production/hosts.yml
$EDITOR ansible/inventories/production/group_vars/all/main.yml
$EDITOR ansible/inventories/production/group_vars/infra_hosts/main.yml

    Set the reserved LAN address, Debian/x86_64 facts, Tailscale tag, K3s node address, management networks, storage declarations, and dotfiles profiles. Keep thinkpad in both infra_hosts and k3s_servers.

  2. Create the encrypted vault

    Copy the variable shape from vault.yml.example, replace required placeholders, encrypt the file, and provide its password only through ANSIBLE_VAULT_PASSWORD_FILE. Never put a Tailscale key in shell history.

  3. Inspect the effective graph

    make inventory
uv run --frozen ansible-inventory \
  -i ansible/inventories/production/hosts.yml \
  --host thinkpad

    Review this locally; do not paste decrypted variables into tickets or chat.

  4. Run repository validation

    make ci

    Fix lint, syntax, unit, link, or contract failures before contacting production.

09 · Ansible convergence

Apply the stable infrastructure profile

From the MacBook, inspect check mode, apply, and validate. The profile limits the site playbook to infrastructure hosts; this ThinkPad participates in baseline, infrastructure, Tailscale, dotfiles, K3s prerequisites, and K3s server plays.

./bootstrap.sh --profile infra --check -- --ask-become-pass
./bootstrap.sh --profile infra -- --ask-become-pass

ANSIBLE_CONFIG=ansible/ansible.cfg \
  "$(uv tool dir --bin)/ansible-playbook" \
  -i ansible/inventories/production/hosts.yml \
  ansible/playbooks/validate.yml --limit thinkpad --ask-become-pass

Baseline and infrastructure

  • Host facts match inventory.
  • Administrator key, UFW baseline, and declared storage are applied.
  • Debian-native Docker packages and bounded logs are configured.
  • Persistent roots and dotfiles revision exist.

Access and cluster

  • Tailscale is authenticated with DNS and Tailscale SSH disabled.
  • K3s uses the checksum-pinned binary.
  • The API uses the LAN identity.
  • The join token remains transient in Ansible.
Review firewall reachability before adding workers. The baseline permits management SSH, while K3s also requires the selected backend’s LAN-only API and inter-node ports. Reconcile explicit UFW policy with the pinned K3s design before treating worker connectivity as production-ready.
Sudo policy is not currently managed. The commands above use Ansible’s interactive become-password prompt. If passwordless automation is later selected, implement and validate a narrowly reviewed sudoers policy through Ansible; do not leave an undocumented manual exception.

10 · Cluster verification

Prove the server before joining workers

ssh homelab@THINKPAD_LAN_IP 'sudo systemctl --no-pager status k3s'
ssh homelab@THINKPAD_LAN_IP 'sudo k3s kubectl get --raw=/readyz'
ssh homelab@THINKPAD_LAN_IP 'sudo k3s kubectl get nodes -o wide'
ssh homelab@THINKPAD_LAN_IP 'sudo ss -lntup'
  • The server reports Ready with architecture amd64.
  • The API address is the reserved LAN address, not a Tailscale address.
  • Pod and service CIDRs match inventory and do not overlap the LAN.
  • /etc/rancher/k3s/config.yaml is root-owned with mode 0600.
  • No token, administrator kubeconfig, or secret appears in captured output.

Join workers only after the server is healthy and backed up. Use the K3s recovery runbook for access, upgrade sequencing, and restore behavior.

11 · State protection

Classify and back up every durable byte

Path or assetMeaningRequired protection
/var/lib/rancher/k3s/server/dbSingle-server SQLite datastore.Consistent off-host backup and clean restore test.
/var/lib/rancher/k3s/server/tokenKey material protecting confidential datastore content.Encrypted backup with the datastore; never Git or logs.
/etc/rancher/k3s/config.yamlServer identity and network configuration.Recoverable from inventory plus protected configuration backup.
/srv/infra/dataDocker databases and service metadata.Service-aware backup, retention, encryption, and application-level restore.
/opt/infra/containersDeployed Compose definitions.Reconcile from reviewed source; protect deployment-only evidence.
Inventory and VaultDesired state and enrollment material on the MacBook.Repository history plus independent encrypted secret recovery.
Do not copy a live database blindly. Each stateful service needs a product-specific snapshot or quiesce method, retention policy, and application-level restore check. A successful file copy is not a backup acceptance test.

12 · Acceptance

Hand off only a rebuildable host

make validate LIMIT=thinkpad
make check PLAYBOOK=ansible/playbooks/site.yml LIMIT=thinkpad

ssh homelab@THINKPAD_LAN_IP '
  systemctl --failed;
  sudo systemctl is-active docker k3s tailscaled ssh;
  sudo docker info;
  sudo docker compose version;
  sudo k3s kubectl get nodes -o wide;
  tailscale status;
  df -h / /srv
'
  • A second Ansible check has no unexplained changes.
  • The host returns after a controlled reboot and stays awake with the lid in its final position.
  • LAN SSH and Tailscale management work; Tailscale SSH stays disabled.
  • Docker, K3s, Tailscale, SSH, time, filesystems, and declared mounts are healthy.
  • The wired Wake-on-LAN path works from the Pi 2 fixed command.
  • K3s state and the initial /srv structure are covered by the selected backup system.
  • Recovery media boots and this guide is available without depending on the ThinkPad.
Setup is complete when recovery is credible. Record Debian and firmware versions, disk identity, reservation, deployed Git revision, K3s pin, backup job, last restore result, and first successful reboot test.
